# Список решений и допущений

Здесь зафиксировано, что в ТЗ допускает разные трактовки и что выбрано
сознательно. Разделы соответствуют сущностям системы.

## Роли и доступ

- **Роли взаимоисключающие.** Пользователь — либо `manager`, либо
  `executor` (ENUM `app_role`), один аккаунт не может совмещать обе.
  В ТЗ допускается «постановщиков и исполнителей может быть несколько»,
  но не сказано, что один человек может быть и тем, и другим; выбрана
  более строгая модель. Если понадобится совмещение — расширяем до
  таблицы `user_roles` или до массива ролей в `profiles`.

- **Черновики задач исполнителю не видны.** Пока менеджер не выполнил
  «Отправить» (`draft → new`), назначенный исполнитель не видит ни
  задачу, ни объект (если у него там нет других, уже отправленных задач),
  ни историю черновика. Это отражено в `can_view_task` и
  `executor_has_task_on_object` через условие `status <> 'draft'`.
  Исполнитель узнаёт о задаче только в момент её постановки — это
  соответствует смыслу статуса «Новая» в ТЗ.

## Объекты

- **Удаление объектов — мягкое (`deleted_at`).** По ТЗ менеджер может
  удалять объекты, но по ТЗ же историю статусов нельзя удалить через API.
  Физическое удаление объекта каскадом уничтожило бы историю связанных
  задач, поэтому используется soft-delete. Физическое удаление возможно
  только вручную через SQL Editor при необходимости.

- **Удаление объекта каскадно мягко-удаляет связанные задачи.** Все
  неудалённые задачи объекта получают `deleted_at` одновременно с
  объектом, чтобы в интерфейсе не оставалось «висящих» задач в
  архивном объекте. При этом удалить объект можно только если на нём
  нет незавершённых задач (всё, что не `accepted`, блокирует удаление).
  Иными словами, каскадно удаляются только уже принятые задачи.

- **Восстановление объекта не восстанавливает задачи.**
  `restore_object` возвращает только сам объект (`deleted_at = NULL`).
  Задачи остаются удалёнными; каждую нужно вернуть отдельно через
  `restore_task`. Это сделано осознанно: объект мог быть удалён давно,
  и автоматически возвращать все его задачи в интерфейс — значит
  вывалить на исполнителей пачку старых задач без предупреждения.
  Альтернатива — каскадное восстановление — отвергнута.

## Задачи

- **После отправки задача заморожена.** Переход `draft → new` фиксирует
  всё содержимое задачи: `title`, `description`, `object_id`,
  `executor_id`, `created_by`, `created_at`. Менеджер не может ни
  отредактировать текст, ни переназначить исполнителя, ни перенести
  задачу на другой объект — только провести её по статусной машине
  (`in_review → accepted` или `in_review → revision`). Если что-то
  пошло не так — задача удаляется и создаётся заново.

- **Смена роли исполнителя после отправки — вне области задания.**
  Если исполнителя, у которого есть активные задачи, перевести в
  `manager` или удалить из `profiles`, его задачи «зависнут»: ни
  исполнитель (уже не `executor`), ни менеджер (не может редактировать
  не-черновик) не смогут двинуть их по статусу. В тестовом задании
  этого сценария нет, роли вручную не меняются. В реальной системе
  здесь понадобился бы либо запрет на смену роли при наличии активных
  задач, либо RPC «переназначить исполнителя у задачи в работе».

- **Удаление задач — мягкое (`deleted_at`).** По тем же причинам, что и
  у объектов: физическое удаление задачи уничтожило бы её историю, а
  историю по ТЗ нельзя удалять через API. Удаление задачи не является
  переходом статуса и не попадает в `task_status_history`.

- **Задача создаётся в `draft` без исполнителя.** ТЗ не запрещает
  назначать исполнителя сразу при создании, но удобнее разделить:
  сначала создать черновик, потом выбрать исполнителя и отправить.
  Это позволяет менеджеру спокойно дописать описание, не опасаясь,
  что исполнитель уже видит задачу (см. выше про невидимость черновиков).
  `send_task` требует, чтобы `executor_id` был задан и указывал на
  пользователя с ролью `executor`.

## История статусов

- **История — append-only через триггер, не через RPC.** Запись в
  `task_status_history` делает только триггер `SECURITY DEFINER` на
  `tasks` (`write_task_status_history`). Клиенту `INSERT / UPDATE /
  DELETE` на эту таблицу не выданы (`REVOKE ALL` + `GRANT SELECT`).
  Подделать, изменить или удалить запись через API нельзя — это
  закрывает п. 4 требований безопасности.

- **Комментарий передаётся в историю через `set_config`.** Так как
  триггер истории не принимает параметров, `transition_task` передаёт
  комментарий через `current_setting('app.task_status_comment', true)`
  на время транзакции. Это единственный способ не дублировать
  бизнес-логику в двух местах (RPC и триггер).

- **Создание задачи тоже пишется в историю** как `NULL → draft`,
  автор — `created_by`. Это даёт полную хронологию «от создания до
  принятия», а не только переходы после постановки.

## Что не успели / сознательно вне области

- Смена роли пользователя при наличии активных задач (см. выше).
- Восстановление объекта вместе с его задачами.
- Экран «Архив» / корзина для восстановления удалённых объектов и
  задач. RPC `restore_object` и `restore_task` есть, но в UI кнопки
  восстановления не выводятся — это следующий шаг после MVP.
- Уведомления (email / push) о назначении задачи и смене статуса.
- Загрузка файлов к задачам.
- Поиск и фильтры в списках объектов и задач.
- Пагинация: списки отдаются целиком, для тестовых объёмов
  (2–3 объекта, несколько задач) этого достаточно.
