# mini-CRM «Объекты и задачи»

Небольшая CRM для строительной компании. Менеджер ставит задачи по
объектам (стройкам), исполнители берут их в работу и отдают на
проверку. Две роли, цикл статусов задачи с историей переходов и
комментарии на каждом шаге.

Стек: **React + TypeScript + Vite**, **Supabase** (Auth, Postgres,
RLS, RPC). Без UI-библиотек, минимальный CSS.

| Роль | Email | Пароль |
|------|-------|--------|
| Постановщик (менеджер) | `manager@example.com` | `12345678` |
| Исполнитель 1 | `executor1@example.com` | `12345678` |
| Исполнитель 2 | `executor2@example.com` | `12345678` |

В базе уже есть 2–3 объекта и несколько задач в разных статусах, чтобы
можно было сразу посмотреть, как система работает в разных состояниях.
Регистрация закрыта — новых пользователей создаёт администратор в
Supabase Dashboard.

## Как устроен проект


src/
├── app/          # AuthProvider, ObjectsProvider, роутер, guards
├── views/        # экраны (Login, ObjectDetail, TaskDetail, MyTasks)
├── services/     # обёртки над Supabase: authService, objectsService,
│                 #   tasksService, usersService
├── components/   # UI-примитивы и диалоги
├── hooks/        # useMyTasks и другие хуки
├── lib/          # supabase.ts — инициализация клиента
├── migrations/   # справочные дампы SQL (функции и RLS-политики)
└── types/        # типы строк БД и словари лейблов


Ключевая идея — **вью только показывают, сервисы только обрабатывают**.
Views не знают про Supabase, services не знают про JSX. Любая ошибка
от Supabase пробрасывается как исключение — конкретное view решает, как
её показать.

### Экраны

| Путь | Роль | Что показывает |
|------|------|----------------|
| `/login` | все | форма входа |
| `/` | все | редирект по роли и наличию объектов |
| `/objects` | обе | пустой экран «выберите объект» / «пока нет объектов» |
| `/objects/:objectId` | обе | карточка объекта + список задач |
| `/objects/:objectId/tasks/:taskId` | обе | карточка задачи + история |
| `/my-tasks` | исполнитель | список задач исполнителя |

Слева — постоянный сайдбар: имя пользователя, «Мои задачи» (только
исполнителю), список объектов (у менеджера — с кнопкой «+ Создать»),
кнопка «Выйти».

### Роли и статусы

Две роли, взаимоисключающие: `manager` (постановщик) и `executor`
(исполнитель). Роль хранится в `profiles.role` и читается из БД, а не
из JWT user_metadata.



| Из | В | Кто | Условие |
|----|---|-----|---------|
| — | `draft` | manager | создание задачи |
| `draft` | `new` | manager | исполнитель назначен |
| `new` | `in_progress` | назначенный исполнитель | — |
| `in_progress` | `in_review` | назначенный исполнитель | — |
| `in_review` | `accepted` | manager | — |
| `in_review` | `revision` | manager | комментарий обязателен |
| `revision` | `in_progress` | назначенный исполнитель | — |

Любой запрещённый переход отбивается на уровне БД (см. ниже) — даже
если отправить запрос в Supabase в обход интерфейса.

Комментарий можно оставить на **любом** шаге. Для возврата на
доработку он обязателен и на клиенте, и на сервере.

## Как защищены данные

Безопасность — обязательная часть проекта, поэтому правила доступа
находятся на уровне базы, а не в интерфейсе.

1. **RLS включён на всех таблицах.** Политики:
   - `objects` — менеджер видит все; исполнитель только те объекты,
     где у него есть хотя бы одна задача в статусе ≠ `draft`;
   - `tasks` — менеджер видит все; исполнитель только свои задачи в
     статусе ≠ `draft`;
   - `task_status_history` — видна тем, кто видит саму задачу;
   - `profiles` — каждый видит свой профиль, менеджер — все.

2. **Чтение — через таблицы, запись — только через RPC.**
   На таблицы выдан `SELECT`, а на `INSERT`/`UPDATE`/`DELETE` — нет.
   Все операции записи (`create_object`, `create_task`,
   `update_task_draft`, `send_task`, `transition_task`,
   `soft_delete_object`, `soft_delete_task` и т.д.) реализованы как
   `SECURITY DEFINER`-функции со своими проверками внутри. Даже если
   обратиться к PostgREST напрямую с JWT исполнителя, прямой
   `UPDATE` не пройдёт.

3. **Переходы статусов проверяются триггером.** `guard_task_update`
   валидирует пару «из какого в какой» и роль актора; на недопустимый
   переход бросает `RAISE EXCEPTION`. Тот же триггер запрещает
   менять содержимое задачи после её отправки (см. раздел ниже).

4. **История статусов — append-only.** В `task_status_history`
   клиент может только читать. Запись делает триггер
   `write_task_status_history` (`SECURITY DEFINER`) на `tasks`.
   Подделать, изменить или удалить запись через API нельзя.

5. **Открытая регистрация отключена.** Пользователей создаёт
   администратор в Supabase Dashboard. Роль назначается UPDATE-ом
   в `profiles`.

6. **Секретов в репозитории нет.** В клиенте только `anon`-ключ,
   `.env.local` в `.gitignore`. `service_role` не используется.

## Отклонения от ТЗ и допущения

Здесь перечислено, что было решено самостоятельно там, где ТЗ
допускает разные трактовки, и что осталось за рамками.

### Флоу создания задачи

- **Двухшаговое создание: `draft → new`.** По ТЗ задача сразу попадает
  в статус «Новая» при создании. В реализации менеджер сначала
  создаёт черновик, затем явно «Отправляет» задачу исполнителю
  (`send_task`). Причина: пока задача в черновике, исполнитель её не
  видит и не начнёт работу раньше времени — можно спокойно дописать
  описание и назначить исполнителя. Это не меняет набор статусов из
  ТЗ, только добавляет внутренний `draft` перед `new`.

- **Черновики невидимы исполнителю.** Условие `status <> 'draft'`
  в RLS-политике `can_view_task` и `executor_has_task_on_object`.
  Исполнитель узнаёт о задаче только после «Отправки».

- **После отправки задача «замораживается».** Поля `title`,
  `description`, `object_id`, `executor_id`, `created_by`,
  `created_at` после перехода `draft → new` менять нельзя. Если нужно
  поправить — задача удаляется и создаётся заново. Причина: не
  хочется, чтобы исполнитель уже работал по одному брифу, а менеджер
  в этот момент менял исполнителя или описание.

### Комментарии

- **Комментарий можно оставить на любом шаге статусной машины**, а не
  только при возврате на доработку. ТЗ этого не запрещает, а на
  практике менеджеру часто нужно что-то добавить при приёмке или
  отправке.
- **Комментарий при возврате на доработку обязателен** — так в ТЗ,
  продублировано и в БД, и в UI.
- **Последний комментарий виден прямо под описанием задачи.**
  Если задача в статусе `revision` и последний комментарий — это
  возврат на доработку, блок выделяется цветом и называется
  «Что доработать». В остальных случаях — нейтральный «Последний
  комментарий». Это не требование ТЗ, а UX-улучшение.

### Роли

- **Роли взаимоисключающие.** Пользователь — либо `manager`, либо
  `executor`. В ТЗ сказано, что постановщиков и исполнителей может
  быть несколько, но не сказано, что один человек может совмещать
  обе роли. Если понадобится — расширяется до таблицы `user_roles`
  или массива ролей.
- **Смена роли исполнителя после отправки задачи не поддерживается.**
  Задача заморожена после `draft → new`, включая `executor_id`.
  Если пользователю с назначенными задачами сменят роль на
  `manager`, его задачи «зависнут»: ни исполнитель (уже не
  исполнитель), ни менеджер (не может редактировать
  не-черновик) не смогут их двинуть. В тестовом задании этот
  сценарий не встречается, роли вручную не меняются.
- **`user_directory` отдаёт email.** По ТЗ это не требуется, но иначе
  в UI вместо имени пользователя показывался бы кусок UUID. View
  доступен всем вошедшим, но не раскрывает ничего, кроме
  `id / display_name / email / role`.

### Удаление

- **Удаление объектов и задач — мягкое (`deleted_at`).** Физическое
  удаление уничтожило бы историю статусов, а её по ТЗ нельзя удалять
  через API. Мягко-удалённые строки из интерфейса не видны.
- **При удалении объекта каскадно мягко-удаляются только его
  принятые задачи.** Если на объекте есть задачи не в статусе
  `accepted`, удаление запрещено (проверка в `soft_delete_object`).
  Принятые задачи уходят вместе с объектом, чтобы не оставлять
  «висящих» записей.
- **Восстановления в UI нет.** RPC `restore_object` и `restore_task`
  есть, но кнопок восстановления в интерфейсе нет. Это следующий
  шаг за пределами тестового задания.

### Устройство интерфейса

- **Сайдбар — это и есть «Список объектов».** По ТЗ «Список объектов»
  — отдельный экран. В реализации список объектов всегда на виду
  в сайдбаре, а «основной экран» — карточка выбранного объекта или
  задачи. Так меньше кликов и не нужно возвращаться назад. Экран
  `/objects` без `:objectId` работает как empty state («выберите
  объект» / «пока нет объектов»).

### Что осталось за рамками

- **Восстановление объектов и задач** через UI.
- **Поиск и фильтры** по списку объектов и задач (кроме табов по
  статусам в «Моих задачах»).
- **Пагинация** — для тестовых объёмов не нужна.
- **Уведомления** (email, push) о назначении задачи и смене статуса.
- **Загрузка файлов** к задачам.
- **Смена исполнителя у задачи в работе.**
